# HTTP, HTTPS, and What Your Browser Really Does

When you type a web address and press enter, your browser starts a conversation in a language called HTTP, the HyperText Transfer Protocol. HTTP is a request-response protocol: the browser sends a request, and a server sends back a response. Each request names a method such as GET, meaning please give me this page, or POST, meaning here is data for you, along with a path and a set of headers describing what the browser wants. Each response carries a status code, headers of its own, and usually a body containing the page.

Status codes are sorted into families, and the first digit tells you the shape of the answer. Codes beginning with 2 mean success, and 200 OK is the everyday "here is your page". Codes beginning with 3 mean redirection, so a 301 tells the browser the page has moved permanently and where to find it. Codes beginning with 4 mean the request was wrong, and the famous 404 means the server understands you but has nothing at that address. Codes beginning with 5 mean the server failed even though your request was fine, and 500 is the generic internal error.

Plain HTTP has a problem: everything is readable in transit. HTTPS fixes that by wrapping HTTP inside TLS, a security layer that encrypts the conversation. When a site uses HTTPS, the content cannot be read or quietly altered by anyone watching the wires, and the site can prove it holds a certificate for that domain. The padlock in your browser is a claim about the connection, not about the honesty of the business behind it.

The browser's job after the response arrives is bigger than it looks. It parses the HTML into a tree of elements, then fetches the stylesheets and builds a second tree describing how things should look. It combines the two into a render tree, calculates the size and position of every box in a step called layout, and finally paints the pixels onto the screen. JavaScript can change the page after this point, which is why pages sometimes shift around while you read them.

Browsers also work hard to avoid repeating expensive steps. A connection opened to a server can be kept alive and reused for many requests instead of starting a fresh one each time. Servers can attach caching headers so the browser remembers images and scripts, and they can send a short validator called an ETag so the browser can ask whether a file has changed and often get back a simple "no, use your copy".

HTTP itself does not remember you between requests; it is stateless. That is deliberate, because statelessness makes servers simpler to scale. To fake memory, a server sends a small piece of data called a cookie, and the browser sends it back on later requests. Cookies let a site keep you logged in across pages, but they are also the mechanism that lets advertising networks recognise you as you move around the web.

So a single page load is a chain of small agreements. DNS finds the server, TCP and TLS build a trustworthy connection, HTTP moves the bytes, and the browser's rendering pipeline turns those bytes into something you can read. Every step is replaceable and inspectable, which is exactly why the web has been so hard to stop.
